# Campfire Architecture

> Архитектурная документация проекта.

---

# Цель

Архитектура Campfire строится вокруг нескольких принципов:

* простота;
* расширяемость;
* читаемость;
* независимость компонентов;
* возможность сохранения полного состояния кампании.

Любое архитектурное решение должно соответствовать этим принципам.

---

# Главная сущность

Главной сущностью приложения является **CampaignState**.

```
CampaignState
│
├── World
├── Characters
├── NPC
├── Enemies
├── Scene
├── Combat
├── Inventory
├── Journal
├── Dice
├── Notes
└── Settings
```

Все игровые системы работают только с этим объектом.

---

# Архитектурные слои

```
UI
│
▼
Controllers (в будущем)
│
▼
Game Systems
│
▼
CampaignState
│
▼
Persistence
```

Каждый слой знает только о нижележащем.

---

# UI

UI отвечает исключительно за отображение информации.

UI не должен:

* рассчитывать игровые значения;
* изменять данные напрямую;
* содержать бизнес-логику.

---

# Game Systems

Игровые системы изменяют состояние кампании.

Примеры:

* CombatSystem
* InventorySystem
* DiceSystem
* QuestSystem
* SceneSystem

Каждая система отвечает только за свою область.

---

# Character

Character — это модель данных.

Он не содержит игровой логики.

Допустимо:

* характеристики;
* навыки;
* эффекты;
* инвентарь.

Недопустимо:

* расчёт боя;
* использование предметов;
* логика заклинаний.

---

# Event System

Любое действие пользователя оформляется как событие.

```
Button

↓

Request

↓

Game System

↓

CampaignState

↓

UI Update
```

Это позволяет позже добавить сетевой режим без изменения архитектуры.

---

# Networking

Используется модель Host / Clients.

```
      GM
       │
 ┌─────┼─────┐
 │     │     │
P1    P2    P3
```

Только ведущий обладает полной копией состояния кампании.

Игроки получают только необходимые данные.

---

# Save System

Сохранение представляет собой сериализацию CampaignState.

Загрузка восстанавливает CampaignState.

Никаких специальных механизмов сохранения внутри игровых систем быть не должно.

---

# Theme

Все визуальные параметры находятся в одном месте.

Запрещается использовать "магические числа" внутри UI.

Например:

❌

```
padding = 7
```

✔

```
Spacing.M
```

---

# Widgets

Все элементы интерфейса проектируются как переиспользуемые компоненты.

Например:

* Button
* Card
* Panel
* CharacterCard
* InventorySlot
* StatRow

---

# Будущие направления

После завершения MVP архитектура должна позволять добавить:

* интернет-подключение;
* плагины;
* новые игровые системы;
* поддержку различных RPG-систем;
* модификации.
